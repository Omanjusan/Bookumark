# 上下2ベイ型ドッキング再設計計画

更新日: 2026-08-01

## 0. 文書の位置づけ

本書は、既存の4方向自由配置型ドッキングベイを実行時から切り離し、上ベイ・下ベイだけを持つ単一構成へ再設計するための確定計画である。

要求分析、現行コード調査、懸念事項インタビュー、仕様確定、TDDテストケース設計、機能別フェーズ分割までを完了している。実装は本書のフェーズごとにGO確認、Red-Green、回帰テスト、記録、コミット文案提示、STAYで進める。

既存の名前付きレイアウト、4方向レール、レイアウト編集、ベイ工場の実装コードと保存データは削除しない。一方、新システムの通常UIおよび起動経路から旧システムへの導線と実行時接続をすべて外す。

正式な表示・手動テスト環境はFirefox、ズーム100%とする。ズーム変更への対応は対象外とする。

## 1. 目的

- 上下2本だけの固定ベイと中央ブックマーク領域へ画面を単純化する。
- 名前付きレイアウトを廃止し、上下ベイの単一構成だけを保存・復元する。
- システムベイによって日常操作への最低限のアクセスを常に保証する。
- 行の非表示とチップ削除を分離し、非表示行の構成を失わない。
- 実位置を見ながら上下ベイを編集できる専用モードを提供する。
- 旧データを移行・破壊せず、新旧システムの境界を明確にする。

## 2. 対象範囲

### 2.1 対象

- 上下2ベイ専用の保存モデル、初期値、正規化、復旧
- 新保存キーによる単一構成の保存とFirefox再起動後の復元
- 上下ベイ、中央ブックマーク領域、固定システムボタンの通常画面
- システムベイの上／下切り替え
- ベイ編集モードとドラフトトランザクション
- 0～3行の表示行数制御
- 非表示行を含むチップの所属行・順序の保存
- タブ式チップツールボックス
- チップ追加、行内・行間・上下ベイ間移動、並べ替え、除去のD&D
- 日付・時計の非機能プレースホルダーチップ
- 初期化、確認、保存失敗、再試行
- 自動テストとFirefox・ズーム100%での手動確認

### 2.2 対象外

- 旧保存データから新保存データへの移行
- 旧名前付きレイアウト、旧4方向ベイ、旧保存データの削除または変更
- 名前付きレイアウトの作成、選択、切り替え、複製、削除
- 左右ベイの表示または編集
- 日付・時計の実際の取得、更新、書式設定
- チップD&Dのキーボード操作
- ズーム変更への最適化
- 最大行数の利用者設定
- 設定画面のシステムベイ切り替えと初期化以外の実機能

## 3. 新旧システムの境界

現行の`src/panel/panel.ts`は、旧保存文書の読み込み、正規化、復旧、activeレイアウト選択、condition適用、4方向描画、レイアウト管理、配置編集、ベイ工場を結合している。

新システムでは次の境界を設ける。

- 通常起動時に旧保存キーを読み込まない。
- 旧データの正規化、復旧、保存、activeレイアウト選択を実行しない。
- 旧4方向レール、レイアウト管理、配置編集、ベイ工場をDOMへ接続しない。
- 旧コードと旧保存データはそのまま残す。
- チップ台帳、チップ描画部品、操作ランタイムなど、名前付きレイアウトと4方向配置に依存しない部品だけを選別して再利用する。
- 新システムの保存、正規化、編集セッション、描画計画は独立したモジュールへ置く。

UIを非表示にするだけでは旧起動処理の切断とはみなさない。新システムの操作、再起動、初期化の前後で旧保存キーが変更されないことをテストする。

## 4. 保存契約

### 4.1 保存キー

新システムは次の独立キーを使用する。

```text
twoBayConfiguration.v1
```

構成全体を1回の`browser.storage.local.set()`で保存する。旧システムの`bayConfigurations.v1`、`mainLayouts.v1`、`dockingMetadata.v1`には触れない。

### 4.2 データモデル

```ts
interface TwoBayConfiguration {
  schemaVersion: 1;
  systemBay: "top" | "bottom";
  nextChipSequence: number;
  bays: {
    top: TwoBayState;
    bottom: TwoBayState;
  };
}

interface TwoBayState {
  visibleRows: number;
  chips: TwoBayChipInstance[];
}

interface TwoBayChipInstance {
  instanceId: string;
  chipType: string;
  row: number;
  order: number;
  settings: JsonObject;
}
```

### 4.3 不変条件

- `systemBay`は`top`または`bottom`である。
- システムベイの`visibleRows`は1～`MAX_BAY_ROWS`である。
- 非システムベイの`visibleRows`は0～`MAX_BAY_ROWS`である。
- `MAX_BAY_ROWS`の初期値は3とし、単一定義で管理する。
- チップの`row`は1～`MAX_BAY_ROWS`である。
- `row > visibleRows`は正常な非表示チップであり、削除または移動しない。
- `instanceId`は構成内で一意である。
- `order`は同一ベイ・同一行の中で順序を表す。
- チップの削除だけがインスタンスを保存構成から除去する。
- 保存へ渡す値と、読み込み後に公開する値には防御的コピーを使用する。

## 5. 初期構成

- システムベイは上ベイとする。
- 上ベイは1行とする。
- 下ベイは0行とする。
- 上ベイ1行目へ次の順序で配置する。
  1. 検索
  2. 訪問状態
  3. フォルダ履歴
  4. ソート
  5. 表示形式
  6. 移動モード
- 日付と時計は初期配置しない。

## 6. 通常画面

- 表示行数が1以上の上ベイと下ベイを、それぞれ画面上端と下端へ固定する。
- 0行の非システムベイは通常画面では完全に非表示にする。
- 中央領域へブックマークを表示する。
- 左上へ`︙`システムボタンを固定し、ベイとは独立してどの通常UIでも表示する。
- `︙`から設定画面とベイ編集へアクセスする。
- 現在の最上位ヘッダー領域も上ベイの配置場所として使用する。
- 旧レイアウト選択、デフォルト復元、レイアウト管理、レイアウト編集、ベイ追加・編集ボタン群を通常画面から撤去する。
- ページ全体はスクロールさせない。
- 各ベイの各行は、横幅不足時に行単位で横スクロールする。
- ベイ内の縦スクロールは設けない。
- 非表示行のチップは描画、状態適用、イベント接続を行わない。

## 7. 設定画面

今回実動作する設定は次の2つに限定する。

- システムベイの上／下切り替え
- 「ベイ状態を初期値に戻す」

それ以外の設定は作らないか、将来領域を示す静的モックに留める。

### 7.1 システムベイ切り替え

- 上下どちらか一方を必ずシステムベイとする。
- 切り替え先が0行なら自動的に1行へする。
- 旧システムベイの行数、表示状態、チップ、所属行、順序、固有設定は変更しない。
- 切り替え結果は単一構成として直ちに保存する。
- 保存失敗時は元の永続状態を変更せず、同じ候補を再試行できるようにする。

## 8. ベイ編集モード

導線は`︙ → ベイ編集 → ベイ構成編集モード`とする。

### 8.1 表示

- 中央のブックマーク、フォルダ、通常中央UIを表示しない。
- 上下ベイを通常時と同じ位置へ固定表示する。
- 中央キャンバスへタブ式ツールボックス、明示的なチップ除去領域、確定、キャンセルを表示する。
- 中央キャンバスの最低寸法は640×360 CSS pxとする。
- 利用可能な縦幅が不足した場合、要素を縮小・衝突させず中央キャンバスだけを縦スクロールさせる。
- ページ全体はスクロールさせない。
- 確定とキャンセルは中央キャンバスの固定フッターとして常に操作可能にする。

### 8.2 編集トランザクション

- 編集開始時に保存済み構成を防御的に複製し、baselineとdraftを分離する。
- すべての編集操作はdraftだけへ反映する。
- 確定時にdraft全体を1回で保存する。
- 保存成功後だけdraftを正式状態へ昇格し、通常画面へ戻る。
- キャンセル時はdraftを破棄し、baselineを完全復元する。
- 保存失敗時は失敗候補を保持する。
- 保存失敗後はD&D、行数変更、追加編集を無効にし、再試行またはキャンセルだけを許可する。
- 再試行は失敗したものと同一の候補を保存する。
- 保存失敗後のキャンセルは失敗候補を破棄し、baselineへ戻す。

## 9. 行数とエクスパンション

- 各ベイの実効行数は0～3行とする。
- 編集モード中だけ、各ベイの左側へ`＋`と`－`を表示する。
- 通常モードでは`＋－`を表示しない。
- 上ベイの`＋`は下側へ1行追加する。
- 下ベイの`＋`は上側へ1行追加する。
- 3行では`＋`を無効化する。
- 非システムベイは1行から`－`を押すと0行になる。
- システムベイは1行で`－`を無効化する。
- 0行では`－`を無効化し、`＋`を有効にする。
- 0行の非システムベイは、編集モードだけ1行相当のプレースホルダーを残す。
- プレースホルダーへ「非表示設定が有効です」とオーバーレイ表示する。
- 0行ベイに対するチップ追加、移動、並べ替え、除去を含むすべてのドロップを無効化する。
- 0行から復帰するには`＋`を使用する。
- `＋－`の画面上の説明文は表示しない。
- `上ベイの行を追加`など、位置と操作が分かる`aria-label`を付ける。

行数を減らしても、チップの所属行、行内順序、固有設定を変更しない。行数を再び増やしたとき、元の所属行と順序で再表示・再接続する。

## 10. チップツールボックスとD&D

### 10.1 タブ

タブは表示カテゴリであり、チップ型そのものとは分離する。初期カテゴリは次のとおりとする。

| タブ | チップ |
|---|---|
| 絞り込み | 検索、訪問状態 |
| ナビゲーション | フォルダ履歴、移動モード |
| 表示 | ソート、表示形式 |
| 情報 | 日付、時計 |

カテゴリとチップ所属はデータ定義から描画し、将来のタブ追加とチップ追加でDOM構造を作り直さずに済むようにする。

### 10.2 日付・時計モック

- ツールボックスから表示中のベイへD&Dできる。
- 通常チップと同じくインスタンスを保存・復元できる。
- ベイ内、行間、上下ベイ間で移動・並べ替えできる。
- 除去領域へのドロップで削除できる。
- 配置後は`日付`または`時計`と分かるプレースホルダーチップを描画する。
- 実際の日付や時刻の取得、定期更新、書式設定は行わない。
- ブックマーク表示状態、共有状態、操作ランタイムへ影響を与えない。

### 10.3 D&D規則

- ツールボックスからの有効なドロップごとに新しいinstance IDを発行する。
- 同じchip typeを複数配置できる。
- 表示中の行だけをドロップ先にできる。
- 行内移動、別行移動、上下ベイ間移動で所属ベイ、row、orderを更新する。
- 明示的な除去領域への有効なドロップだけが対象インスタンスを削除する。
- 中央領域外、ベイ間の隙間、無効な対象へのドロップでは構成を変更しない。
- ベイ自体は削除できない。
- チップD&Dのキーボード操作は対象外とする。

## 11. 初期値へ戻す

- 設定画面のシステムベイ選択付近へ「ベイ状態を初期値に戻す」ボタンを配置する。
- 実行前に破壊的操作であることを示す確認ダイアログを表示する。
- キャンセルでは何も変更しない。
- 承認後、初期値候補を作り、単一構成として一括保存する。

初期化対象は次のとおりとする。

- システムベイ指定
- 上下ベイの行数と表示・非表示状態
- 非表示行を含む全チップ構成
- チップの所属行と行内順序
- チップ固有設定
- 未確定の編集draft
- 保存失敗候補

旧名前付きレイアウト、旧4方向ベイ、旧保存キー、ブックマーク、ドッキング以外の設定には触れない。

初期化保存に失敗した場合は初期値候補を画面に保持し、追加操作を無効化して再試行可能にする。保存成功までは元の永続構成を変更しない。

## 12. 正規化と復旧

読み込み時に次を検証する。

- 文書形式とschema version
- `systemBay`
- 上下ベイの存在
- `visibleRows`の整数性と範囲
- システムベイが1行以上か
- instance IDの形式と重複
- chip type
- rowの範囲
- orderの整数性と重複
- settingsがJSONオブジェクトか
- next sequenceが既存IDと衝突しないか

復旧規則は次のとおりとする。

- 新保存キーがない場合は内部初期値を生成する。
- 旧保存キーだけが存在しても移行せず、内部初期値を使用する。
- 文書全体が解釈不能な場合は初期値候補へ復旧し、保存前に通知する。
- 行数だけが範囲外なら0～3へ補正し、システムベイは最低1へ補正する。
- rowが範囲外なら1～`MAX_BAY_ROWS`へ補正する。
- 未知チップは削除せず保持するが、描画・実行しない。
- 日付と時計は既知のモックチップとして描画する。
- order重複は保存配列順を安定した補助順序として再採番する。
- 正規化結果の保存に失敗した場合は候補を保持して再試行可能にし、通常ランタイムを開始しない。

## 15. フェーズ進行規則

各Phaseは次の順序で進める。

1. 対象Phaseの完了条件とテストケースを確認する。
2. ユーザーの明示的なGOを得る。
3. 期待する未実装理由で失敗するテストを追加し、Redを確認する。
4. 同じGOの範囲で最小実装を行い、Greenを確認する。
5. 対象テストに加えて全回帰テストを実行する。
6. 必要な文書と進捗記録を更新する。
7. コピー可能なコミット文案を提示してSTAYする。

既存の未コミット変更は破棄、上書き、巻き戻ししない。変更が重なる場合は実装を止めて確認する。
