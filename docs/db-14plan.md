## 確定仕様

### 1. 共通通知の使い分け

- ユーザー確認、復旧保存、再試行が必要な通知は共通ダイアログを使う。
- 通常操作を止めないcondition失敗などの警告は共通トーストを使う。
- ダイアログは同時に1件だけ表示し、起動時の優先順でキュー処理する。
- トーストは通知IDと集約キーを持ち、同一内容を重複DOMとして増やさない。
- 警告トーストは8秒後に自動消去し、エラートーストは手動で閉じる。
- トーストはフォーカスを奪わず`aria-live`で通知する。
- ダイアログは見出し、説明、主操作をアクセシブルネームで関連付け、開いた際に安全な操作へフォーカスする。
- ダイアログを閉じられない保存待ち状態では、Escapeや背景操作で復旧フローを迂回させない。
- 内部reasonと例外詳細は画面へ露出せず、構造化データを`console.warn`へ残す。

### 2. 起動順序

1. 3つの保存文書を読み込む。
2. 既存の依存順正常化を実行し、構造復旧結果を得る。
3. 現行チップ台帳と廃止台帳を使い、全ベイのチップを分類する。
4. unknownチップを除外した復旧候補を作り、必要な構造復旧とまとめて保存する。
5. unknown／構造破損の復旧ダイアログを表示する。
6. 保存失敗時は同一候補の再試行を待ち、通常runtimeへ進まない。
7. 保存成功後、deprecatedチップを適用・描画しない状態で確認ダイアログを表示する。
8. deprecated確認後の削除保存が成功したら、保存済み文書から通常runtimeを構築する。
9. condition失敗があればruntime構築後に警告トーストを表示する。

unknownがなく構造正常化だけが発生した場合も、正常化済み文書の保存成功後に復旧内容をダイアログで通知する。復旧対象がなければダイアログを表示せず起動する。

### 3. チップ台帳と分類

```ts
type DeprecatedChipRecord = {
  chipType: string;
  displayName: string;
  deprecatedSince: string;
  removedSince: string;
  replacementChipType?: string;
};
```

- 現行台帳はruntimeで解決可能な全`chipType`と表示名を保持する。
- 廃止台帳は実装削除後もレコードを削除しない。
- 現行台帳にある型を`current`、現行にはなく廃止台帳にある型を`deprecated`、どちらにもない型を`unknown`とする。
- 同じ`chipType`が現行台帳と廃止台帳の両方にある場合は設定不良としてテストで拒否する。
- 廃止台帳内の`chipType`重複も設定不良として拒否する。
- 日付は通知表示用の台帳情報とし、検出可否を現在の拡張バージョン比較だけに依存させない。
- 初期台帳に実在する廃止チップがない場合、プロダクション台帳は空で開始し、テストでは注入した台帳を使う。

### 4. unknown／破損復旧

- unknownチップはベイ名、`chipType`、件数を集約する。
- unknownチップだけを全ベイから除外し、残るチップの相対順を維持して各ベイ内`order`を1始まりで再採番する。
- ベイID、正常チップのinstance IDとsettings、採番カウンター、レイアウト配置、メタデータを暗黙に変更しない。
- 既存正常化で除外・補正・文書フォールバックが発生した場合も復旧サマリーへ含める。
- 正常化不能時は注入済み内部デフォルト文書へフォールバックする。
- 復旧候補と入力文書は状態を共有しない。
- 復旧が必要な文書だけを1回のstorage要求で保存する。
- 保存成功後に復旧完了として扱い、次回起動で同じunknown通知を繰り返さない。
- 保存失敗時は候補を作り直さず防御的コピーで同一内容を再試行する。

### 5. deprecated確認と削除

- deprecatedチップは確認中も描画・condition適用・control接続・action実行をしない。
- 1つのダイアログへベイ名、表示名、インスタンス件数、`removedSince`、代替候補を集約する。
- 同種が複数ベイ・複数インスタンスに存在しても1回の確認で全対象を扱う。
- 主操作は「確認」とし、自動置換や個別維持は提供しない。
- 「確認」で全deprecatedインスタンスを削除したベイ文書候補を作り、残るチップを連続orderへ再採番する。
- 保存中は確認の再実行とダイアログ終了を停止する。
- 保存成功後だけダイアログを完了状態へし、通常runtimeへ進む。
- 保存失敗時は元文書、削除候補、ダイアログを維持し、「保存を再試行」を表示する。
- 対象インスタンスが保存済み文書から消えること自体を確認済み記録とし、別のacknowledgedフラグは保存しない。

### 6. condition失敗通知

- 既存の`DockingConditionFailure`を、適用列の`bayId`とベイ文書からベイ名へ解決する。
- チップ表示名は現行台帳から解決し、解決不能時は安全な代替表示を使う。
- runtime再構築1回に生じた失敗を警告トースト1件へ集約する。
- 表示内容は失敗件数、対象ベイ名、チップ名の要約とする。
- `reason`、instance ID、例外詳細は`console.warn`の構造化情報に残す。
- condition失敗は対象チップだけをその評価で無効化し、後続condition、control接続、メイン表示を継続する。
- 同じ集約キーのトーストが表示中なら新規要素を増やさず、発生回数と最新要約を更新して8秒を再計時する。
- conditionがない、または失敗が0件なら通知しない。

### 7. 共通通知基盤の拡張境界

- 通知モデルは`info`、`success`、`warning`、`error`の重要度を表現できるようにする。
- ダイアログは確認、再試行、処理中、完了を表現できるようにする。
- トーストは手動終了と任意の自動終了時間を表現できるようにする。
- DB-14ではDocking復旧とcondition失敗だけを実接続する。
- 既存の公式移動通知、ロード失敗、保存失敗などの全面移行は別フェーズへ残す。

## テストケース設計

### 正常系

- 現行6チップをすべて`current`へ分類する。
- 注入した複数世代の廃止台帳から飛び級対象を検出する。
- unknownだけを除外し、正常チップ、ベイ、配置、メタデータを維持する。
- 複数ベイの同種deprecatedを1ダイアログへ集約する。
- deprecated確認保存後に全対象が消え、次回検出されない。
- condition失敗をベイ名・チップ名付きの1トーストへ集約する。
- 警告トーストが8秒後に消える。

### 異常系

- 現行台帳と廃止台帳の重複を拒否する。
- unknown復旧保存失敗でruntimeを開始せず、同じ候補を再試行できる。
- deprecated削除保存失敗でダイアログと対象を維持し、同じ候補を再試行できる。
- 既存正常化が文書全体をフォールバックした場合に内部デフォルトを保存・通知する。
- 通知描画失敗を復旧候補や保存済み文書の破壊へ波及させない。
- conditionのベイ名・表示名を解決できなくても通知処理を停止しない。

### 境界値

- 空の廃止台帳、空ベイ、チップ0件では復旧通知を出さない。
- 同一ベイにcurrent、deprecated、unknownが混在してもcurrentだけを維持する。
- 同種unknown／deprecatedが多数あっても型・ベイ単位に集約する。
- unknown除外後またはdeprecated削除後に空ベイとなってもベイと配置を維持する。
- 全ユーザーチップが除外されても内部デフォルトへ不必要に切り替えない。
- replacementがない台帳項目でも案内を生成できる。
- 長いベイ名・チップ名でもダイアログとトーストが操作不能にならない。

### 再実行・整合性

- 復旧関数を同じ正常化済み文書へ再適用しても変更されない。
- 保存アダプターが候補を変更しても再試行内容が変化しない。
- unknown復旧成功後の再起動で同じ通知を出さない。
- deprecated削除成功後の再起動で同じ通知を出さない。
- 保存失敗後の再起動では保存中インスタンスから再検出して通知する。
- 入力文書、台帳、失敗配列を変更しない。
- unknown／deprecatedは適用列、描画計画、interaction実行へ到達しない。

### アクセシビリティ

- ダイアログの見出し、説明、主操作、再試行がアクセシブルネームで取得できる。
- 保存待ちダイアログをEscapeで迂回できない。
- ダイアログ終了後に適切なフォーカス位置へ戻る。
- トーストがフォーカスを奪わず`aria-live`へ通知される。
- 手動終了可能なトーストをキーボードで閉じられる。

### パネル統合

- 起動順が構造正常化、unknown保存、deprecated確認・保存、runtime構築となる。
- 復旧保存中・失敗中に通常チップ操作とメイン表示を開始しない。
- 復旧成功後は保存済み文書からactiveレイアウトを1回だけ構築する。
- condition失敗後も後続condition、基本control、ブックマーク表示が動く。
- 復旧不要時は既存起動経路と保存要求回数を増やさない。
