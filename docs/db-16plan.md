# DB-16「既存エラー経路の共通通知移行・公式整理凍結」計画

## 1. 状態

- 状態: `DB-16A_COMPLETE`
- 要求分析: 完了
- 懸念事項インタビュー: 全6問完了
- 仕様・テストケース: 確定
- 実装許可: DB-16A取得済み、DB-16B〜H未取得
- 次の作業: DB-16B「共通通知アダプターと固定文面・診断」のテストケース確認とRed-GreenのGO確認
- 前提: DB15-E-01Gは`DB15-E-01G_FROZEN_WITH_KNOWN_LIMITATIONS`として凍結済み

## 2. 背景

DB-14で共通通知キュー、共通ダイアログ、共通トースト、Docking起動復旧、condition失敗通知を実装した。一方、既存の読み込み失敗と仮想カスタム順序の保存失敗には、中央の専用エラー表示またはコンソール出力だけの経路が残っている。

DB-16では、利用者が継続可否とデータ状態を判断できるよう、対象エラーを共通通知へ移行する。通知履歴などの新機能は追加せず、既存の共通通知基盤を正本として利用する。

要求分析中、Firefox公式DBを書き換える「公式整理」は、Bookumark内の表示整理という価値に対して、部分成功、正本再取得、外部変更、Undo競合、Firefox Syncなどの復旧責務が過大であると判断した。公式整理は正式機能から外して凍結し、仮想カスタムだけを正式な並べ替え機能とする。

## 3. 目的

- 初期読み込み失敗を、再試行可能な共通ダイアログへ移行する。
- フォルダ移動・履歴移動の読み込み失敗時に、移動前の表示と履歴を維持して共通トーストで通知する。
- ブックマークとフォルダの仮想カスタム順序保存失敗を、共通トーストで通知する。
- 同種失敗を集約し、利用者向け画面へ内部情報を露出しない。
- 公式整理を利用者向けUIから外し、起動時に安全な移動モードへ戻す。
- 開発ビルド限定の一回限りの失敗fixtureで、Firefox実機検証を決定的に再現する。

## 4. 確定したプロダクト判断

### 4.1 対象エラー

DB-16で共通通知へ移行するのは次の2系統とする。

1. ブックマーク、現在フォルダ、仮想順序などの読み込み失敗
2. ブックマーク／フォルダの仮想カスタム順序保存失敗

### 4.2 通知形式

| 失敗 | 通知 | 理由 |
| --- | --- | --- |
| 初期起動の読み込み | 共通エラーダイアログ | 通常操作を開始できず、明示再試行が必要 |
| フォルダ移動・履歴移動の読み込み | 共通エラートースト | 移動前表示を維持して操作を続けられる |
| 仮想カスタム順序の保存 | 共通エラートースト | 画面上の並びを維持し、次の並べ替えで再保存できる |

初期読み込み失敗時に中央の専用エラー表示を重複表示しない。読み込み中表示はダイアログ背後に残してよいが、操作可能な通常表示へは進めない。

### 4.3 再試行

- 初期起動失敗は、ダイアログの「再試行」でブックマークツリー、保存設定、現在フォルダを最初から再読み込みする。
- 初期再試行中は主操作を無効化し、多重実行を防止する。
- 初期再試行が再び失敗した場合は、同じダイアログを維持して再試行可能状態へ戻す。
- フォルダ移動、履歴移動、仮想順序保存は自動再試行しない。
- 仮想順序は現在の画面上で維持し、次の並べ替え操作が最新全量を保存することで再保存機会とする。

### 4.4 利用者向け文面と診断

- 初期読み込み: 「Bookumarkの読み込みに失敗しました。再試行してください」
- フォルダ移動・履歴移動: 「フォルダを読み込めませんでした。元の表示を維持しています」
- 仮想順序保存: 「表示順を保存できませんでした。現在の並びはこの画面で維持されています」
- 内部ID、例外文、storageキー、フォルダ名、ブックマーク名を通知本文へ表示しない。
- 原因となった例外と操作種別はコンソール診断へ残す。
- 同種トーストは操作種別ごとの固定`aggregateKey`で集約し、既存UIで発生回数を表示する。
- `error`トーストは既存契約どおり自動終了せず、利用者が閉じる。

### 4.5 公式整理の凍結

- 仮想カスタムを唯一の正式な並べ替え機能とする。
- 移動モードUIから「公式整理」を非表示にする。「通常」は並べ替えを行わない表示として維持できる。
- 起動・再構築時に`directory-move`が渡された場合は`custom-order`へ安全に正規化する。
- 正規化はFirefoxブックマーク、仮想順序、ベイ・レイアウト文書を変更しない。
- 公式移動、Undo、正本再取得の実装コードと自動テストは削除せず凍結する。
- 公式整理の成功通知、失敗通知、UndoをDB-16の共通通知移行対象に含めない。

公式整理を再開する条件は次のすべてが揃うこととする。

- Firefox本体を書き換える明確な利用者需要
- 移動結果不明、部分成功、再取得失敗の復旧契約
- 外部変更とFirefox Syncを含む競合方針
- Undo可能期間とUndo不能時の説明
- 実機で再現可能な障害fixtureと受け入れ基準

### 4.6 開発用失敗fixture

- 開発ビルド限定fixtureページへ、一回限りの初期読み込み失敗と仮想順序保存失敗を準備する操作を追加する。
- スイッチは対象経路で1回発火した時点で自動解除する。
- 二重準備しても無制限に失敗回数を積み上げない。
- production manifest、production panel、production配布物へfixture UIと実行コードを含めない。
- fixture終了・既存DB-15退避復元の責務を混在させず、失敗スイッチだけを独立して解除できるようにする。

## 6. 状態・整合性契約

### 6.1 初期読み込み

- 初期読み込みを1つの再実行可能な操作境界として扱う。
- 途中まで取得したツリー、フォルダ、仮想順序、Docking runtimeを通常操作可能な正本として公開しない。
- 失敗時は共通ダイアログをactiveにし、成功時だけ通常runtimeを1回開始する。
- 再試行成功後はダイアログを完了し、待機中の既存通知を順序どおり表示する。

### 6.2 フォルダ・履歴移動

- 移動先読み込み開始前のブックマーク、フォルダ、現在フォルダ、履歴位置をスナップショットとして維持する。
- 読み込みまたは現在フォルダ保存に失敗した場合はスナップショットへ戻す。
- 失敗した移動を履歴へ追加せず、戻る／進むの現在位置も進めない。
- エラートースト描画失敗を、復元済み表示や履歴へ波及させない。

### 6.3 仮想カスタム順序保存

- D&D後の画面上の並びを先に反映する既存の楽観表示を維持する。
- 保存失敗で画面上の並びを自動ロールバックしない。
- 保存済み正本を成功扱いに更新せず、次回の全量保存で現在表示の順序を送る。
- ブックマーク用とフォルダ用の失敗を同じ利用者文面で通知してよいが、診断では操作種別を区別する。
- 通知失敗が保存処理や現在表示へ例外として逆流しない。

## 8. 懸念事項と確定対応

| 懸念 | 確定対応 |
| --- | --- |
| 移行対象を広げると各編集セッションの再試行設計まで膨らむ | 読み込みと仮想順序保存の2系統へ限定する |
| 初期失敗をトーストにすると操作不能理由と再試行が不明確 | 初期失敗だけ共通ダイアログにする |
| フォルダ移動失敗で現在表示や履歴を失う | 移動前スナップショットへ戻してからトーストを出す |
| 保存失敗で画面順序を戻すと利用者操作が失われる | 楽観表示を維持し、次の全量保存を再保存機会にする |
| 例外文に内部IDや個人データが含まれる | 画面は固定文面、詳細はコンソール診断だけにする |
| 同じ失敗でトーストが増殖する | 固定`aggregateKey`で既存トーストへ集約する |
| 公式整理の安全性を通知UIだけで解決しようとする | 正式機能から外し、コードを凍結する |
| 過去状態が公式整理を再選択する | runtime境界で`custom-order`へ正規化する |
| 失敗経路をFirefox実機で再現できない | 開発限定・一回限りの失敗fixtureを用意する |
| fixtureがproductionへ混入する | buildと配布物の否定テストを置く |
| 通知表示自体の失敗が元処理へ波及する | 通知アダプター境界で隔離し、診断へフォールバックする |

## 9. TDD方針

- 初期読み込みはruntime開始、再試行、多重防止を扱うためTDD必須とする。
- フォルダ・履歴移動は表示、現在フォルダ、履歴の整合性を扱うためTDD必須とする。
- 仮想順序保存は楽観表示と保存済み正本を分けるためTDD必須とする。
- 公式整理凍結はUI、runtime正規化、保存非変更をRedで固定する。
- 開発fixtureは一回限り、自動解除、production除外をRedで固定する。
- 各実装フェーズは`GO確認 → Red → Green → 対象テスト → 全体回帰 → progress.md更新 → コミット文案 → STAY`で進める。
- 小規模でRedが意図どおり成立した場合は、ユーザーがRedのみのSTAYを指定しない限り、同じGOでGreenとテストまで続けてよい。
